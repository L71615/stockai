# CEO Plan: 研究到决策证据闭环
Generated by /plan-ceo-review on 2026-07-24
Branch: main | Mode: SELECTIVE EXPANSION
Repo: L71615/stockai

## Problem

StockAI 已能自动运行 GP/ML 研究、因子衰减检查、数据健康检查、简报和通知，但候选因子仍缺少可追溯的前向证据链。当前 `factor_candidates.promoted` 主要是布尔标记，回测结果多为瞬时返回，缺少冻结假设、样本外运行记录、组合级前向跟踪和可解释晋级依据。

本计划要回答：自动研究产出是否在未见过的数据上持续改善决策，而不是继续增加候选数量。

## Vision

### 10x Check

打开 `/pipeline` 时，不只是看到“昨晚跑了多少个因子”，而是看到一条可信证据链：某候选何时冻结、使用了哪个数据和成本版本、在负对照和三种市场状态下表现如何、影子组合相对基准怎样、当前是否建议晋级，以及上一轮审批后的结果。

### Platonic Ideal

StockAI 是个人量化研究实验室：研究假设先冻结，所有候选经过样本外验证、负对照、成本压力和市场状态分层；通过后进入按固定规则运行的影子组合；系统持续比较当前 Champion 与候选 Challenger；系统只提出晋级、降级、退役建议，由用户确认；复盘结果会回流到下一轮研究。

## Approach

采用 **演进式证据闭环**，不建设完整券商模拟撮合系统。影子组合按固定收盘价、统一成本和调仓规则计算，目标是验证信号有效性，而不是模拟排队、撤单、部分成交和券商 API。

复用：
- `services/quant_pipeline.py` 的 `PipelineStatus` 编排和进度状态
- `strategy_backtest_service._evaluate_overfit()` 的样本外判定
- `factor_lifecycle.py` 的 active/warning/retired 规则
- `quant_service.get_benchmark_comparison()` 的基准比较逻辑
- `quant_brief.py`、`notify_service.py` 的简报和通知
- `review_service.py`、`trading_memory.py` 的复盘与决策记忆

实现约束：最多新增 `experiment_service.py` 和 `shadow_portfolio_service.py` 两个业务服务；优先扩展 `/factor-lab` 和 `/pipeline`，不先建设新的量化工作台；所有新增表同时写入 `database/schema.sql`，不再把表定义隐藏在初始化代码中。

## Accepted Scope

### Phase 1: Evidence ledger
- 实验、运行、候选快照和数据/成本/代码版本可追溯。
- 候选状态不再用单一布尔或混合状态表达；采用 `lifecycle_status`、`portfolio_role`、`proposal_status` 三轴，首个 Champion 由用户从通过最低 Gate 的 `paper` 候选中显式确认。
- 所有状态迁移记录时间、操作者、规则版本、证据摘要和理由。

### Phase 2: Validation gates
- 统一样本外验证结果持久化，不接受只有内存返回的指标。
- 负对照：多个固定种子的随机表达式、简单基准和标签置换；通过率和多重搜索校正必须入账。
- 市场状态：bull/bear/sideways；样本不足显示 `unknown`，不得强行评分。
- 成本压力：基础/保守/极端成本，周/月调仓敏感性；矩阵版本必须入账。
- 数据健康、数据缺失、样本不足、负对照失败时禁止晋级。

### Phase 3: Shadow portfolio
- 收盘后生成信号，下一可交易日执行；统一使用公共交易日历、qfq 前复权、T+1、整手、现金、涨跌停/停牌未成交、手续费和滑点规则；这些输入的版本必须与每日结算一起保存。
- 每日保存现金、目标仓位、实际权重、换手、净值、回撤和相对基准。
- 影子组合不是实盘，也不自动下单。

### Phase 4: Human approval inbox
- `/pipeline` 展示待审批建议：候选、建议动作、证据、风险、数据新鲜度和规则版本。
- 服务端为审批 proposal 发放带 TTL 的 lease；同一 lease 的重试幂等，撤回/过期后重开生成新 lease，提交时原子校验 proposal、candidate 和 evidence 版本。
- 接受/拒绝/稍后处理都记录操作者和理由。
- 证据更新后旧建议标记过期，不能用旧快照确认新状态。
- 默认不自动晋级、不自动替换当前策略。

### Phase 5: Champion/Challenger
- Champion 与 Challenger 使用同一观察窗口、基准、成本和市场状态划分比较；v1 Gate 要求 forward 至少 60 个交易日且至少 8 次独立决策，Champion 替换建议至少 120 个交易日且至少 12 次独立决策。
- Champion/Challenger 产生的替换建议与普通晋级、降级、退役建议共用 Phase 4 审批收件箱；不建设第二套审批 UI。
- 样本不足、数据健康异常、负对照失败或成本压力不通过时不得替换。

### Phase 6: Retrospective
- 扩展现有月报和交易记忆，记录每次晋级/拒绝/替换之后的真实前向结果。
- 复盘必须区分研究指标、影子组合指标、基准表现和用户实际决策结果。

## Dependencies and Ordering

```text
experiment freeze
  → validation ledger + negative controls
  → cost/regime gates
  → shadow portfolio forward records
  → approval inbox
  → champion/challenger comparison
  → retrospective feedback
```

Champion/Challenger 不得在没有稳定 Champion、最小观察窗口和可用影子组合记录前启用。任何自动任务失败都必须留下明确的 failed/partial/blocked 状态，不能生成看似成功的日报。

## Acceptance Criteria

- 每个候选可查询冻结快照、验证运行、数据版本、成本版本和状态迁移历史。
- 样本外、负对照、市场状态、成本压力任一失败时，候选不能晋级。
- 影子组合可按日重放，结果包含净值、换手、成本、回撤和基准差。
- 审批动作重复提交、过期建议、网络中断和页面离开后不会产生重复或错误状态迁移；同一审批页重试复用 `approval_attempt_id`，离开或撤回后必须使用新的 attempt。
- Champion/Challenger 只生成建议，不自动替换；替换建议可追溯到同一验证窗口。
- Pipeline、API、数据库写入、定时任务和前端页面均覆盖 loading/empty/error/success 或对应失败状态。
- 至少有 API 集成测试、纯函数测试、数据重放测试和一条手动触发到复盘的 E2E 测试。
- 简报明确区分 `done`、`partial`、`blocked`、`stale`，通知失败不能掩盖研究失败。

## NOT in Scope

- 真实券商 API、实盘下单、自动交易。
- 完整撮合引擎、部分成交、撤单队列和公司行动模拟。
- Alpha158 全量移植、跨市场验证、在线学习。
- 无证据的自动晋级、自动退役或自动替换。

## Implementation Notes

- 统一错误命名：`ValidationDataError`、`ValidationInsufficientSampleError`、`ValidationNegativeControlError`、`ApprovalConflictError`、`ShadowPortfolioSettlementError`；关键路径不得只 `except Exception` 后返回空结果。
- 实验关系：一个 `experiment` 可包含多个版本化 `validation_run`；一个候选可在多个独立 experiment 中重复验证，但每次运行必须保存完整输入快照和规则版本。
- 统一审批幂等 key：改为服务端 `approval_proposal_id + action + approval_lease_id`；租约有 TTL，网络重试复用同一 lease，撤回或过期后重新打开生成新的 lease；提交必须原子校验 proposal/candidate/evidence 版本，冲突返回 409。
- 交易日历从 `backend/routers/data_ops.py:51` 提取为公共纯工具；新验证链不得直接复用默认 `user_id=1` 的 `quant_service.get_benchmark_comparison()`。
- 新增 `validation_policy.py` 纯规则模块，统一版本化的 `CostPolicy`、`RegimeClassifier`、`TradingDayPolicy`、`PromotionGate`；不新增第三个业务服务。
- Phase 1 的状态拆为三个轴：`lifecycle_status`（candidate/validated/rejected/blocked/stale/retired）、`portfolio_role`（none/baseline/champion/challenger/paper）和 `proposal_status`（pending/approved/rejected/expired/withdrawn）；状态迁移使用版本 CAS 和允许迁移表。
- 主终点预注册为：净成本后相对 Baseline Policy v1 的风险调整超额收益。Baseline Policy v1 冻结沪深 300 总收益和候选股票池等权组合；用户真实采纳/拒绝作为独立 `proposal_outcome` 评估，不混入基线。
- Point-in-time 输入和独立 OOS 是 P1：冻结当时股票池、上市/退市覆盖、数据源/抓取时间、复权/公司行动可用版本、配置和 snapshot hash；冻结配置后独立重算 validation/forward 信号，不能只切同一条 equity curve。
- v1 Gate 预注册：forward 至少 60 个交易日且至少 8 次独立决策；Champion 替换建议至少 120 个交易日且至少 12 次独立决策；负对照使用多个固定种子和标签置换，置信区间/多重搜索失败时返回 unknown 或 blocked，不得晋级。
- 影子组合采用最低限度 A 股执行语义：收盘后生成信号、下一可交易日执行；实现 T+1、整手、现金约束、涨跌停/停牌未成交事件和分项费用。无法满足时标记 `research_only`，禁止作为 paper performance 或晋级依据。
- `/pipeline` 前端页面目前不存在，本计划包含新建该页面、历史运行、证据详情、审批收件箱和对应 API/TypeScript 类型；UI 必须遵守 `DESIGN.md` 的信息层级、四态/partial/stale、键盘和移动端要求。
- 每日任务设置单飞锁、候选/矩阵/运行时预算、并发 semaphore、公共行情缓存；超时保留已完成证据但标 `partial/blocked`，禁止晋级。
- 采用“扩展 → 只读验证 → 开关启用 → 收缩”发布；新表先加，shadow/approval 由 feature flag 控制，回滚只关开关并保留 append-only 证据。
- Scope #1 的 CC 估时按 Phase 映射拆分：Phase 1 账本与 schema ~60 分钟、Phase 2 验证门 ~60 分钟、Phase 3 影子组合 ~90 分钟、Phase 4 审批与 API/UI ~60 分钟、Phase 6 复盘与测试 ~90 分钟；Phase 5 Champion/Challenger 包含在 Phase 4 的审批与比较工作中，总计仍以 4–6 小时为目标，超出即暂停新增扩展。
- 原计划的 20 个交易日门槛由 v1 Gate 的 60/120 交易日和有效决策数取代；任何替换建议仍必须经过 Phase 4 审批。

## Deep Review Decisions

### Architecture and failure contracts

- `PipelineStatus` 只负责进程内实时 telemetry；experiment、validation、approval、settlement 的业务事实必须持久化，数据库是唯一事实源。
- 新增错误/恢复矩阵：数据源 timeout/429、SQLite locked/constraint、缺价、样本不足、证据过期、通知失败分别定义重试、阻断、降级、用户提示和测试；`partial`、`blocked`、`stale` 不得进入晋级门。
- 新增对象级授权：实验、影子组合和审批读写全部带 `user_id` ownership；候选全局读写仍按业务权限；审计记录 actor、request/run id、旧状态、新状态、理由和 evidence version。
- 影子结算分类处理：合法停牌可沿用上一有效价格并标 `stale`；未知缺价阻断当日证据；portfolio + observation_date + input_version 唯一键防重复结算。

### Delivery gates

- Gate 1：单候选冻结、point-in-time 输入、独立 OOS、单一保守成本、可重放影子组合、持久 run、双基线比较和最小证据 UI。
- Gate 2：负对照扩展、bull/bear/sideways 分层、三档成本/周月调仓矩阵、审批租约与收件箱、Champion/Challenger 和复盘。
- 若 Gate 1 无法产生可信证据，停止 Gate 2，不继续堆 UI 或竞争机制。

### Required quality, tests, and operations

- 共享规则层使用无 IO 纯函数并固定测试向量；所有研究/影子结果带 policy version/hash。
- 测试包含 unit、DB integration、point-in-time leakage assertion、独立 OOS replay、A 股 T+1/整手/涨跌停、重复审批并发、过期证据 CAS、进程重启和通知失败注入。
- 轻量可观测性首日交付：run_id/experiment_id/lease_id 日志、运行时、候选数、Gate 通过率、负对照失败、stale/blocked 结算、基准差、审批积压、最近成功运行；现有通知渠道只用于阈值告警。

## Error & Rescue Registry

| Codepath | Failure | Exception / State | Rescue | User sees |
|---|---|---|---|---|
| Load point-in-time data | timeout / 429 | `ValidationDataError` | bounded retry with backoff; then `blocked` | 数据不可用，未生成晋级证据 |
| Validate sample | empty / too few days / coverage unknown | `ValidationInsufficientSampleError` | persist `unknown`/`blocked`; no PASS | 样本不足，继续积累证据 |
| Run negative controls | control failure / search correction failure | `ValidationNegativeControlError` | mark run invalid; prevent promotion | 验证器自检失败 |
| Persist evidence | SQLite locked / constraint / version conflict | `DatabaseLockedError` / `ApprovalConflictError` | retry transaction; rollback; return 409 or failed | 保存失败，未改变状态 |
| Settle shadow day | missing price / calendar mismatch | `ShadowPortfolioSettlementError` | classify legal halt as stale; unknown price blocks day | 结算 stale/blocked |
| Create approval proposal | stale evidence / duplicate | `ApprovalConflictError` | compare proposal/evidence version; idempotent no-op or 409 | 提案已过期，请刷新 |
| Submit approval | expired lease / wrong owner | `ApprovalConflictError` / `AuthorizationError` | reject atomically; audit attempt | 无权或租约已过期 |
| Notify | SMTP/Telegram/WeCom failure | `NotificationError` | keep evidence status; retry separately | 研究已保存，通知失败 |
| Pipeline worker | process restart / unhandled step error | `PipelineRunFailed` / `partial` | DB lease recovery; finally writes terminal state | 运行中断，禁止晋级 |

规则：任何 `partial`、`blocked`、`stale`、`research_only` 结果都不能生成晋级或替换建议。关键路径禁止用裸 `except Exception` 返回空成功值。

```text
  ├─ nil/missing ──▶ ValidationDataError ──▶ blocked
  ├─ empty pool ───▶ insufficient_sample ──▶ unknown
  ├─ valid ────────▶ independent OOS ──▶ gates ──▶ shadow settle
  └─ upstream error ▶ retry ──▶ failed/partial ──▶ no promotion

shadow settle:
  signal after close ─▶ next tradable execution
       ├─ valid quote ─▶ cash/lot/T+1/fee ─▶ snapshot
       ├─ legal halt ──▶ carry last price + stale ─▶ no promotion
       ├─ unknown quote ▶ blocked ─▶ retry same input version
       └─ duplicate key ▶ existing snapshot + audit ─▶ no double cost
```

### State machine

```text
lifecycle_status: candidate ─▶ validated ─▶ paper ─▶ retired
                         ├────▶ rejected
                         ├────▶ blocked ─▶ validated (new run)
                         └────▶ stale ───▶ validated (new evidence)
portfolio_role: none ─▶ baseline | paper | champion | challenger
proposal_status: pending ─▶ approved | rejected | expired | withdrawn

Rules:
- exactly one active Champion per user/policy scope;
- no proposal from blocked/stale/research_only evidence;
- replacement is suggestion + approval, never automatic;
- every transition uses version CAS and append-only audit.
```

### Error flow

```text
specific exception
      ├─ retryable ─▶ bounded retry/backoff ─▶ success or partial
      ├─ data-invalid ─▶ blocked/unknown ─▶ visible UI + no promotion
      ├─ conflict ─▶ rollback + 409 ─▶ refresh/retry with new lease
      └─ notification-only ─▶ evidence remains saved ─▶ channel retry
```

### Deployment sequence

```text
backup + fresh/legacy schema smoke
  ▶ additive tables/indexes
  ▶ deploy code with shadow/approval flags OFF
  ▶ read-only replay and dual-read comparison
  ▶ enable Gate 1 for one candidate
  ▶ verify metrics + manual approval
  ▶ enable Gate 2 expansions
  ▶ remove compatibility only after stable evidence window
```

### Rollback flow

```text
metric/settlement alarm
  ▶ disable shadow/approval flag
  ▶ stop scheduler lease acquisition
  ▶ preserve append-only evidence
  ▶ keep existing pipeline/report path available
  ▶ inspect runbook + replay fixture
  ▶ fix forward or git revert
  ▶ never DROP evidence tables as rollback
```
